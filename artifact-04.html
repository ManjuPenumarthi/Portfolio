Navigating Real-World ML Data Challenges: A Scenario-Based Coaching Session

ARTIFACT 04

My other artifacts show how I evaluate AI tools, reason about ML vs. DL, and scope whether AI is worth investing in at all. This artifact goes a level deeper: the hands-on technical judgment calls that come after a project is greenlit and real, messy data shows up. Working through three scenarios with an AI coach, I reasoned through the actual decisions a data scientist has to make when a dataset has missing values, when a model is quietly failing on a rare-but-critical class, and when a previously accurate model starts drifting in production — the kind of problem that shows up in ERP and reporting systems just as often as it does in consumer ML.

Description A one-on-one coaching session with an AI-driven scenario bot covering three common machine learning data challenges: (1) handling a dataset where 20% of values in a key feature (income) are missing for a customer churn model, (2) diagnosing and fixing a fraud detection model that hits 99.5% accuracy by predicting "not fraud" for every transaction, and (3) explaining why a housing price model that performed well in testing started underpricing homes in a rapidly gentrifying neighborhood six months after deployment.
Objective To demonstrate practical, technically-grounded decision-making for the data problems that most directly determine whether an ML model is trustworthy in production — missing data, class imbalance, and concept/data drift — rather than treating these as abstract textbook definitions.
Process
  • Missing data (churn model): reasoned that the fix depends on why the data is missing — checking whether missingness correlates with other features before choosing a strategy — and proposed median imputation paired with a "missing" indicator flag as a defensible first pass, rather than defaulting to dropping 20% of the dataset.
  • Class imbalance (fraud detection): identified that 99.5% accuracy was misleading given only 0.5% of transactions were fraudulent, and that the model was exploiting the imbalance rather than learning fraud patterns. Proposed moving off accuracy entirely in favor of precision/recall/F1 and PR-AUC, and recommended starting with class weighting before layering in SMOTE-based oversampling or threshold tuning.
  • Data drift (housing price model): diagnosed the underpricing issue in a gentrifying neighborhood as data drift — the relationship between features and price shifting faster than the model's training data reflected — and recommended confirming the drift was localized, retraining on recent data, and setting up ongoing monitoring so drift is caught earlier than a six-month lag next time.
Tools & Tech AI Scenario Coaching Bot (SchoolAI.com), applied data science reasoning, statistical evaluation metrics (precision, recall, F1, PR-AUC), imputation and resampling strategy (SMOTE, class weighting)
Value Proposition This artifact shows I can reason through the technical judgment calls that sit underneath any AI/ML system I'd propose or evaluate — not just whether to use AI, but how to keep a model honest once real data and real drift show up. That's directly relevant to any reporting, forecasting, or anomaly-detection logic built into ERP systems like NetSuite, where "clean" training conditions never survive contact with production data.
Unique Value Where Artifact 02 shows conceptual judgment (ML vs. DL) and Artifact 03 shows business-case judgment (should we invest in AI at all), this artifact fills the gap between them: the practical, in-the-weeds reasoning a developer needs once a model is actually being built and monitored — the stage where most production ML failures actually happen.
Relevance As I bring more structured AI/ML practice into NetSuite development, this is the layer I'll rely on most directly: recognizing when a dataset's missing values need more than a quick fix, catching a model that's gaming its own metric, and knowing to watch for drift in any system trained on historical business data that keeps changing underneath it.
